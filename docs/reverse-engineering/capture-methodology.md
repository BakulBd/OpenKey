# Capture methodology

How to record and analyse traffic so that every protocol claim has evidence behind it.

## Rules

1. **One change per experiment.** Change exactly one setting between "before" and "after".
2. **Controlled inputs.** Use the test assets below, not arbitrary images or colours.
3. **Record state.** Write down the keyboard state before and after, and what you saw on the keyboard.
4. **Never guess packets at the hardware.** Captures come from the official software; OpenAK820 only
   sends what has been traced or captured. Unknown commands are documented, never "tried".
5. **Confidence is earned.** Findings start as UNVERIFIED and are promoted in the research log only with
   evidence (CONFIRMED needs a hardware observation).

## Recording

### Official Windows driver (primary source for discovery)

Run the official driver in a Windows VM with the keyboard passed through, and capture on the Linux
host with usbmon:

```
tools/capture/usbmon-capture.sh 0c45:8009 captures/03-rgb-red-blue.pcapng
# perform exactly one change in the official tool, then Ctrl+C
pnpm tsx tools/capture/src/pcap-to-experiment.ts captures/03-rgb-red-blue.pcapng \
  --id 03-rgb-red-blue --before "static red" --after "static blue" --effect "keys turned blue"
```

USBPcap + Wireshark on Windows works too; feed the `.pcapng` to the same converter.

### OpenAK820 itself

`OPENAK820_DEBUG=1 openak820 <command>` prints every report with timing; `--json` output contains the
packet log. In the browser, Diagnostics → _Download report_ exports the same.

## Experiment record

Each record (`tools/capture/src/experiments.ts` → `ExperimentRecord`) carries: experiment id, timestamp,
device identity (VID, PID, product, bcdDevice), host OS and tool, interface/endpoint, direction,
report type (feature set/get, output, input), report ID, raw bytes, decoded bytes when known, operation
name, before state, after state and the observed effect.

## Differential analysis

```
pnpm packet-diff captures/03-red.json captures/03-blue.json [--only host]
```

Output: packet count difference, changed offsets per aligned packet, stable/variable offsets, shared
header, length-field candidates, counter/address candidates and checksum candidates (sum8, xor8,
two's complement). The tool never names a byte; naming happens in the research log once a second
experiment confirms it (for example a brightness sweep shows exactly one offset moving in steps of one).
